# Channel manager selection for v1

Resolves ticket `.scratch/hotel-pms-v1/issues/03-channel-manager-selection.md`.
Researched 2026-09-24 against vendor developer portals, live API endpoints and vendor price lists. Anything not backed by a primary source is marked **UNVERIFIED**.

Scope: which third-party channel manager v1 should integrate for two-way sync of rates, availability, restrictions and reservations with OTAs, for European independents and small chains (Germany/DACH first, up to 400 rooms per property).

## Recommendation: Channex.io for v1

**Pick Channex.io** as the single v1 channel-manager integration, and design the rates model so that a SiteMinder pmsXchange adapter can be added later without schema changes.

Why Channex:

1. **Fastest, cheapest path to a certified two-way integration.** Public REST docs, self-service staging, no partnership contract needed to start, no certification fee, and a published 14-test certification with a live screenshare [C1][C8][C10]. SiteMinder requires a signed agreement before onboarding and budgets ~60 days to production; DIRS21, HNS and Lighthouse have no public developer programs at all [S1][S14].
2. **It is built for PMS vendors, not hotels.** Channex is wholesale-only and white-label: the PMS owns the hotel relationship and billing (USD 130/month + USD 7/property) [C10][C11]. This fits a multi-tenant SaaS where channel management is a feature of the PMS. Every other candidate sells to the hotel directly; the PMS is one of many "Schnittstellen" and the hotel pays extra for it (DIRS21: "ab EUR 295" on request, plus partner-side module fees) [D4][D6][D7].
3. **The rate model is the richest and closest to what a modern PMS needs**: explicit per-room/per-person sell modes, derived rate plans with amount/percent modifiers, inheritance flags per restriction, and both arrival- and through-based min stay. Nothing we need to express is lost in the mapping [C3][C6].
4. **Event-driven ingestion is well specified**: webhooks as triggers, booking revisions feed with explicit ack, out-of-order and retry semantics documented [C4][C5]. That maps cleanly to an outbox/inbox design in Postgres.
5. **DACH channel coverage is adequate for v1**: HRS, Booking.com, Expedia, Airbnb, Google, plus channel codes for DIRS21, TOMAS and Feratel [C13][C14]. Gap: Hotel.de is not listed separately (it belongs to HRS Group; whether the HRS connection covers it is **UNVERIFIED**).

Why not the others for v1:

- **SiteMinder pmsXchange** is the strongest second choice and the best "chain-grade" option (47,000+ properties, push reservations, payment transaction records). But it is SOAP/OTA XML, needs a partnership agreement, mapping is configured on SiteMinder's side, and it does not support stay-through min stay or derived rates, so the PMS must expand every derived rate to full amounts [S1][S6][S7]. Plan it as the second adapter once v1 has paying customers; nothing in the recommended rates model blocks it.
- **DIRS21** has the deepest DACH footprint (5,300+ customers, HRS top-tier partner) and would be the right *second* adapter for German independents. But its PMS API is an undocumented .NET SOAP service (V2 publicly reachable; V3 only described by other PMS vendors), V2 has no stop-sell/max-stay fields, and every hotel pays an "on request" PMS-interface fee [D1][D2][D4]. Budget a DIRS21 adapter for v2 when German sales demand it; the operations list in [D1] shows it is a small surface (11 operations).
- **HotelNetSolutions RateDistributor** has no public API or partner program; integration is negotiated per PMS [H2][H4]. Not suitable as the first integration for a new PMS.
- **Cubilis / Lighthouse** is Benelux-centred, the legacy integration lacks CTA/CTD, and the new Integration API is partner-gated with unpublished terms [L5][L1]. Lowest DACH relevance of the five.
- **"Apaleo-connected options"**: Apaleo is a PMS, not a channel manager; its store carries Channex, SiteMinder, DIRS21 Channelswitch and RateDistributor as apps [C15][S18][D5][H5]. That confirms all four are viable PMS-side integrations but is not itself a candidate.

Confidence: **high** on Channex being the best v1 choice on cost, docs and speed; **medium** on long-term DACH sales fit, because German hotels often already have a DIRS21 or HNS contract and may expect the PMS to talk to it (plan the DIRS21 adapter early). EU data residency for Channex must be confirmed contractually before onboarding EU tenants (UNVERIFIED).

## Constraints on the PMS rates model

Design the internal model so it can be projected onto Channex without loss, and so a later SiteMinder/DIRS21 adapter is a strict subset:

- **Hierarchy is Property → Room Type → Rate Plan.** Availability lives on the room type (Channex `availability` per `room_type_id`; SiteMinder `InvTypeCode`; DIRS21 per room). Rates and restrictions live on the rate plan (Channex `restrictions` per `rate_plan_id`; SiteMinder room-rate). Do not model per-rate-plan inventory as a first-class concept; if needed, express it as Channex `max_availability`/`availability_offset` on the rate plan [C2][C3][S11].
- **Per-property limits**: keep hotels within 20 room types and 200 rate plans per property or accept overage fees; per-person occupancy up to 18 [C7]. 400-room hotels fit if room *types* stay under 20.
- **Rate plan occupancy ≤ room type occupancy** or Channex rejects the rate plan [C2].
- **Sell mode is a property of the rate plan**: `per_room` (one price) or `per_person` (price per occupancy 1..n with a primary occupancy). Store a list of `(occupancy, price)` options and a flag for the primary occupancy [C3]. SiteMinder OBP caps this at 5 adults and needs an "included occupancy" per room-rate; DIRS21 extended writes carry `Occupancy` per `RateDetail` [S6][D1]. So the PMS needs: base occupancy, extra-adult and child pricing per rate plan.
- **Derived rates**: model `parent_rate_plan_id` plus an ordered list of modifiers (`increase/decrease_by_amount|percent`) and per-field inheritance flags (rate, CTA, CTD, stop_sell, min_stay_arrival, min_stay_through, max_stay). Channex can evaluate these natively; SiteMinder and DIRS21 cannot, so the PMS must also be able to **materialise derived rates to absolute daily values** before pushing [C3][S6].
- **Restriction vocabulary (superset to store)**: `stop_sell`, `closed_to_arrival`, `closed_to_departure`, `min_stay_arrival`, `min_stay_through`, `max_stay`. Channex accepts all; SiteMinder accepts only arrival-based min/max LOS, CTA, CTD, stop sell; DIRS21 V2 accepts `MinStay`, `CTA`, `CTD` only (stop sell = `Available 0`). Treat `min_stay_through` as optional and degrade to arrival-based on adapters that lack it [C3][S5][D1].
- **Restrictions can be weekday-patterned** (Channex: 7-element arrays; SiteMinder: day-of-week flags). Store restrictions per date; let adapters compress into ranges/patterns [C3][S5].
- **Rates are decimal strings in the rate plan's ISO-4217 currency**; no currency conversion happens downstream (SiteMinder applies amounts as sent). One currency per rate plan [C2][S6].
- **Meal plan is a rate-plan attribute** (Channex `meal_type` enum) [C3].
- **Taxes**: Channex has a tax-set on the rate plan and bookings carry `taxes[]` with `is_inclusive`; SiteMinder wants `AmountBeforeTax` or `AmountAfterTax` consistently. The PMS must know for each rate plan whether stored prices are gross or net [C3][C5][S6].
- **Date-window**: push at least the next 500 days (Channex full-sync test) and be prepared for 750 days (SiteMinder) [C8][S5].
- **Change propagation must be delta-based and event-driven**: keep an ARI outbox keyed by (property, room type/rate plan, date); coalesce changes per property every ~6–60 s; hard limit 10 restrictions + 10 availability calls per minute per property (Channex) and "within 2 minutes" freshness (SiteMinder). Timer-based full syncs fail Channex certification; a nightly full push is allowed [C2][C8][C16][S7].
- **Booking ingestion must be idempotent and ack-based**: store `booking_revision_id`, OTA reservation code and `status` (`new`/`modified`/`cancelled`); process, then ack; webhooks only trigger a pull. Per-night prices, occupancy (adults/children/infants), services and taxes arrive per room and must be preserved on the reservation [C4][C5].
- **Card data** is only delivered to PCI-DSS-certified partners via a separate secure endpoint; v1 should not take card data from Channex (use OTA virtual cards / payment links instead) [C5].
- **Booking constraints on the reservation model**: a booking can contain multiple rooms with differing rate plans and per-day prices; the PMS reservation must support room-level line items with a daily price breakdown [C5][S9].
- **External IDs**: keep a mapping table `channel_manager_ref` (provider, external property/room type/rate plan ID, internal ID) so that a second adapter (SiteMinder codes, DIRS21 `UID`/`PMSCode`) can coexist per property [S11][D1].
